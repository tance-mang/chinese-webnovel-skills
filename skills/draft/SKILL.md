# 供修改的 Word 草稿（draft）

定位：**AI 先写个"大概"的草稿供人筛选修改**，不是定稿。按作者的排版习惯导成 Word，并标出可改的地方。

## 何时用
- 把小说/章节导成 Word(.docx)
- 要分章节、带目录、章标题左对齐
- 要 AI"标出可以改的地方"让作者自己改
- "先写个大概我来看看，再筛选修改"

## 输出规则（按作者习惯，务必遵守）
1. **格式 = Word(.docx)**。
2. **绝不覆盖原文**：命名 `《书名》修改1.docx`，已存在就自增 `修改2`、`修改3`…
3. **目录**：自动插入（Word 里右键目录→更新域 生成页码）。
4. **章标题用普通文字“第1章 章名”并左对齐**。Word 使用 Heading 1 样式，不加 Markdown 井号、装饰线、星号或自动编号。聊天中的可复制稿也使用这个格式。
5. **正文与建议分离**：默认正文只保留小说内容，修改建议保存到独立文件，按章和段首短语定位。只有作者明确需要行内批注版时才使用 `【修改：建议】`。
6. **字数**：已有稿件按原长导出，不补写凑字数。仅在作者要求完整短篇草稿且未指定长度时，参考总量 8000–30000、草稿 10000–20000；不是单章下限。各档篇幅/签约门槛见 `references/length-standards.md`（如番茄短故事 ≥6000、爽款 1万–1.8万）。

## 在哪里标"修改"建议
草稿里给自己挑刺，常见可改处（借 review/annotate/deslop 的眼光）：
- 节奏偏慢、铺垫过长 → `【修改：这段铺垫偏长，可删减】`
- 开头/章尾钩子弱 → `【修改：章尾再留个钩，比如…】`
- 情绪在"喊"没"演" → `【修改：'我很难过'建议改成动作，见 emotion】`
- 无缘无故的修辞 / 不搭的引用 → `【修改：这个比喻可删】`
- 爽点/打脸不够 → `【修改：此处可加一拍围观反应】`
- 可扩可删的弹性段 → `【修改：此处可扩写到XX字 / 可精简】`

## 工作流
1. 先确认：书名、频道/平台/题材、**人称（沿用作者选择）**、目标字数。
2. 已有稿件只转换格式，不擅自重写、改人称或补剧情。需要起草时只写作者约定范围，沿用既有人称与长度要求；没有要求时不为导出而扩成完整短篇。章标题使用“第1章 章名”，建议独立存放。
3. 把草稿存成 markdown，例如 `书名.md`。
4. 运行脚本生成 Word：
   ```bash
   python "${CLAUDE_PLUGIN_ROOT}/skills/draft/build_docx.py" 书名.md --title "书名" --outdir "你的输出文件夹"
   ```
   （缺库先 `pip install python-docx`。）
5. 告诉作者：生成的文件名、正文字数、有几处【修改】建议。

## 原则
- **是草稿不是定稿**：写"大概"，把精修留给作者；用【修改】把你的判断显式标出来，而不是替作者拍板。
- **永远新建文件**，不动原稿——作者的版本由作者掌控（也可配合 `memory` 的 git 快照）。
- 短篇控制在 8000–30000，草稿停在 10000–20000 留余地。

## 其它模型（ChatGPT/DeepSeek 等不能跑脚本时）
输出普通文字章标题和干净正文，建议另列，避免将井号、分隔线、评分或修改标记混入复制稿。不宣称已生成不可用的 Word 附件。

## 下一步
作者改完 → 可再 `review` 复诊、`memory` 存档/快照。


## 作者主导与输出约定

遵守仓库根目录 `references/author-led-workflow.md` 的版本与采用规则。教学、备选和诊断不混入小说正文。已有作者要求优先，不要求每个小步骤重新确认。
